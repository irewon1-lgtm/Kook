# 3. 앱을 켜면 이렇게 쓴다

사용자 설명서 3/5

## 1. 회사 이름을 검색한다

회사 이름·종목코드·별칭으로 찾는다. 종목을 누르면 “어떤 회사 / 무엇이 달라졌나 / 가장 큰 위험”이 먼저 나온다.

## 2. 열 가지 숫자로 줄을 세운다

기본은 10지표 종합 순위다. 원하는 지표만 켜거나 끄고 비중을 바꿀 수 있다. 매출 증가율 하나만 켜면 그 기준만으로 비교한다. 앱이 몰래 다른 지표를 켜지 않는다.

## 3. 점수 옆의 이유를 읽는다

“10지표 순위 점수”와 “매수 검토 / 매도 검토 점수”는 다르게 표시한다. 80점은 돈 벌 확률 80%가 아니다. 위험이 큰 회사는 높은 성장 점수 옆에 경고가 먼저 보인다.

## 4. 자세한 보고서를 펼친다

짧은 요약 아래에 사업 구조, 이익과 현금이 달라진 이유, 빚, 주식 수 증가, 가격 부담, 반대 근거와 다음 확인 조건이 나온다. 긴 글을 작성하고 화면에서 잘라 버리지 않는다.

## 5. 차트·뉴스·공시·관심종목을 확인한다

차트에 실적 발표·계약·증자 같은 사건을 겹쳐 보고, 뉴스와 공시의 원문을 연다. 관심종목을 저장하면 나중에 달라진 점부터 확인한다.

증권사 앱에서 기대하는 조회·분석·차트·호가·수급·알림·모의 포트폴리오를 기능 명세에 넣었다. 실시간 호가·실계좌 조회는 자료 이용권과 계정 연결이 필요하다. 실제 주문은 별도 승인 없이는 켜지지 않는다. [S03, S04]

낙폭이 크다고 자동으로 좋은 점수를 주지 않는다. 기본 순위는 낙폭이 작은 쪽을 높게 본다. “많이 떨어진 회사 찾기”는 별도 검색 조건이다. 은행과 제조업처럼 계산 의미가 다른 경우에는 같은 잣대로 억지 평가하지 않는다.

| 순서 | 앱 뒤에서 하는 일 | 네가 보는 것 |
| --- | --- | --- |
| 1 | 취소 공시를 읽고 원래 계약과 연결 | “계약 취소 공시가 새로 나옴”. |
| 2 | 예전 보고서의 수주·성장 근거를 찾음 | 기존 보고서에 “새 자료 검토 중”. |
| 3 | 취소가 매출·현금에 미치는 영향 검토 | 취소 이유, 영향, 아직 모르는 것. |
| 4 | 관련 문단과 바이셀 점수를 다시 계산 | 왜 판단이 달라졌는지 비교. |
| 5 | 한 묶음으로 저장한 새 버전을 앱이 읽음 | 새 버전 번호와 기준 시각. |

위 표는 동작 설계 예시다. 실제 기업의 사건을 처리했다는 뜻은 아니다. 가격만 바뀌면 가격에 연결된 숫자와 가격 평가를 고친다. 회사 실적이 그대로면 매출 수치는 그대로인 것이 정상이다.

## 돈이 필요하다고 하면 네 가지만 받는다

① 어디에 연결하는지 ② 이번 비용 상한 ③ 매월 비용 상한 ④ 실패했을 때 되돌리는 방법. 승인 전의 추가 과금 한도는 0으로 둔다. ChatGPT 구독과 별도 API 요금은 분리돼 있다. [S14]

중요한 새 발견: 금융위원회 공공 시세 안내는 실시간이 아니며 다음 영업일 오후 1시 이후 갱신이라고 명시한다. 제3자 무단 제공·재배포 제한도 있다. 무료 자료를 가져왔다고 실시간 가족 앱이 자동 완성되는 것은 아니다. 정확한 범위를 확인하고 필요한 권리를 확보해야 한다. [S05]

여기까지가 사용자가 먼저 읽을 설명이다. 다음 쪽부터는 개발자에게 넘길 세부 제작 기준이다.

# 10. 추가 2지표에서 특히 조심할 것

국내주식 앱 V3 | 제작 기준

## ROIC의 세율과 자본

표준 모드는 NOPAT=TTM 영업이익 × (1 - TTM 법인세비용 / TTM 세전이익)이다. 세전이익이 양수이며 세율이 0~50% 범위에 있을 때만 이 세율을 사용한다. 이 범위는 법정세율 주장이 아니라 이상치 검토 정책이다.

영업손실이면 실현되지 않은 세금 혜택을 더하지 않는 보수적 정책으로 세율 0을 사용하고 표기한다. 그 외 비정상 세율은 REVIEW로 둔다. 정상화 세율을 따로 추정하면 ESTIMATED_ROIC로 분리하고 표준 순위에 조용히 넣지 않는다.

기초·기말 투하자본이 모두 양수여야 한다. 평균 투하자본이 연매출의 1%보다 작으면 작은 분모로 값이 폭발할 수 있어 CAPITAL_BASE_THIN으로 검토한다. 이 임계값도 초기 설계값이며 사후 성과에 맞춰 몰래 고치지 않는다.

## 순차입금/EBITDA가 위험을 숨기지 않게

순차입금 200, EBITDA -100이면 -2배이지만 좋은 재무구조라는 뜻이 아니다. 음수 분모는 점수를 만들지 않는다. 순현금 회사에서 EBITDA가 0에 가까워 -1000배가 나와도 -2배 회사보다 무한히 우수하다고 평가하지 않는다.

## 은행·보험·금융회사

은행의 부채와 산업기업의 빚은 같은 사업 의미가 아니다. 공통 10지표 중 부적합 항목은 NOT_APPLICABLE로 유지한다. 금융사는 별도 사업 모델로 분리하고 ROE·자본 적정성·부실자산·손해율·P/B 등 확인 가능한 업종 자료로 분석한다. [S07: 재무변수 정의를 기초로 한 설계 판단]

공통 10지표 공식 순위에 금융사를 억지로 합치지 않는다. 금융사도 검색·가격·뉴스·공시·분석 대상에는 포함한다. 업종 전용 순위를 만들면 별도 정책 이름으로 공개하고 기존 10개를 몰래 교체하지 않는다.

# 11. 순위가 공정하려면 비교 규칙이 고정돼야 한다

국내주식 앱 V3 | 제작 기준

## 1. 먼저 비교 반을 정한다

동일 사업 모델 안에서 산업 → 상위 업종 → 같은 모델 전체 순으로 넓힌다. 해당 지표의 유효 비교 기업이 30개 이상인 첫 모집단을 사용한다. 30은 초기 최소 표본 정책이다. 금융/산업 모델은 섞지 않는다. 어느 반과 비교했는지 표시한다.

## 2. 지표별 백분위를 만든다

좋은 방향으로 정렬한 평균 등수 r, 실제 유효 기업 수 n에 대해 지표 점수 = 100 × (r - 1) / (n - 1). 동점은 평균 등수. n<2이면 점수 없음.

예: 세 회사 값이 10, 10, 30이면 큰 값이 좋은 지표의 점수는 25, 25, 100이다. 결측 기업은 이 지표의 분모 n에 넣지 않는다. 가격·비교 모집단·회계 정책·공개시점은 스냅샷에 고정한다.

## 3. 다섯 분야에 20점씩 배분한다

| 분야 | 지표별 가중치 |
| --- | --- |
| 주가 흐름 20 | Q01 10 + Q02 10 |
| 성장 20 | Q03 20 |
| 수익성과 자본 효율 20 | Q04 5 + Q05 5 + Q06 5 + Q09 5 |
| 가격 부담 20 | Q07 20 |
| 주주 몫과 재무 안정 20 | Q08 10 + Q10 10 |

비슷한 수익성 지표가 많다는 이유만으로 총점 대부분을 차지하지 않도록 묶었다. 가중치는 과학적으로 유일한 정답이 아니라 공개한 초기 정책이다. 사용자 변경 시 새 정책 ID를 만들고 기본값을 보존한다.

검색·화면 필터는 이미 계산한 점수를 숨기거나 보여줄 뿐이다. 검색했다는 이유만으로 원점수를 다시 계산하지 않는다. 선택 지표 변경은 의도적 재계산이므로 비교 정책과 선택 항목을 명시한다.

# 12. 자료가 비어도 가짜 우등생을 만들지 않는다

국내주식 앱 V3 | 제작 기준

## 공식 순위와 참고 범위를 분리

기본 공식 순위는 선택된 10지표가 모두 비교 가능하고 유효한 기업끼리 매긴다. 선택을 3개로 바꾸면 그 3개가 모두 있는 기업의 맞춤 순위다. 금융사·신규상장·자료 부족 기업을 앱에서 삭제하지 않는다.

고정 가중치 w의 합=1. 확인한 지표만 합한 하한 L=sum(w×지표점수). 상한 U=L+100×미확인 가중치. 완전 자료일 때 L=U=종합점수. 일부 자료일 때 “확인 범위 42~67점, 자료 75%”처럼 표시한다.

이 범위는 통계적 신뢰구간이 아니다. 모르는 지표가 0~100일 수 있다는 계산상 범위다. 모르는 원자료 자체를 0으로 저장했다는 뜻도 아니다. 낮은 값 하나가 빠져도 확인 하한이 올라가지 않는 성질을 시험했다.

## 절대 하지 않는 계산

한 종목의 없는 지표만 빼고 남은 항목을 다시 100점으로 늘리지 않는다. “매출 증가율 하나가 좋아서 종합 강한 매수”를 만들지 않는다. 점수 범위가 넓으면 정확한 공식 등수가 있는 것처럼 줄 세우지 않는다.

## 통계와 화면의 추가 조건

동점은 같은 순위로 표시하고 종목 ID는 화면 순서만 안정화한다. 숫자의 화면 반올림으로 내부 계산을 덮어쓰지 않는다. 원값·단위·출처·기여 점수와 “순위가 왜 달라졌나”를 모두 열어 볼 수 있게 한다.

분기별로 지표 간 상관과 업종 편중을 점검하되, 그때 수익률이 잘 나온 조합을 자동으로 골라 기본 가중치를 바꾸지 않는다. 사용자 설정의 예측력과 기본 모델의 예측력은 별도로 검증한다.

# 13. 매수·매도 점수는 하나의 동전이 아니다

국내주식 앱 V3 | 제작 기준

정량 순위는 계산으로 재현 가능하다. 미래 사업 해석과 적정가치 판단에는 가정과 판단이 남는다. AI가 완전히 객관적인 투자 확률을 만든다고 설명하지 않는다.

| 점수 | 초기 정책 · 0~100 | 필수 해석 |

| 매수 검토 B | 0.40×정량 Q + 0.25×사업 경쟁력 + 0.20×가치 대비 여유 + 0.15×촉매 | 같은 시점·모델의 정량 점수 사용. 사업·가치·촉매마다 근거 필수. |

## 표시 규칙

중대 위험·거래정지 등은 경고가 최우선이다. 중요한 새 정보가 미검토이면 REVIEW_PENDING. B≥70과 S≥60이 함께 충족되면 의견 충돌. S 하한≥70이면 매도 검토 우선. B 전 항목 확인·B≥70·S 상한≤40이면 매수 검토. 나머지는 관찰로 표시한다.

70/60/40은 임시 운영 정책이지 수익이 입증된 경계값이 아니다. 적정가치 자료가 없으면 그 축은 범위로 남긴다. 독립적인 과거검증·전진검증 전에는 “연구용·성과 미검증”을 표시한다. 위험 경고를 점수 부족 때문에 숨기지는 않는다.

모델은 근거와 판단 근거를 작성한다. 최종 산술은 서버 코드가 수행한다. 모델이 임의로 총점을 출력하거나, 뉴스 개수만으로 매수 점수를 올리게 하지 않는다.

## 작성과 검토를 다른 역할로 나눈다

1. 허가된 원문을 읽어 사실·기간·회사·숫자를 추출한다. 2. 서버 계산 결과와 결합한다. 3. 작성 모델이 기업별 인과관계를 설명한다. 4. 검토 단계가 숫자·회사·전망/실적 혼동·논리 비약·반대 근거 누락을 검사한다. 5. 오류가 있는 문단만 수정한다.

## 관련성·중요도·시점의 순서

회사 식별이 먼저다. 중요 사건을 묶고, 공개 시점과 사건 시점을 따로 고려한다. 동일 보도자료를 복제한 기사 5개는 독립 근거 5개가 아니다. 오래됐지만 아직 유효한 중대 사건은 날짜를 드러내고 별도 카드로 유지한다.

우선 최근 30일을 검색하고 부족하면 90일·365일로 넓히되 기간 확장을 표시한다. 고정 최신 공시 2개가 형식 공시뿐이면 중요한 최근 실적·정정·계약 공시도 별도 노출한다. 원문 제목만 있는 경우 본문 요약인 척 쓰지 않는다.

웹에서 열리는 자료라도 수집·저장·가공·AI 처리·가족 제공·공개 재배포 권한은 따로 확인한다. 로그인·유료벽·접근제한을 우회하지 않는다.

## 회사의 숫자와 보고서를 한 번 묶는다

지표 객체는 ID·값·단위·기간·공개시각·회계 범위·통화·원자료 ID·계산식 버전·상태·사유를 가진다. 화면은 Q01 같은 ID로 이름을 찾는다. JSON 입력 순서로 이름표를 붙이지 않는다.

| 상태 | 사용자에게 보여줄 의미 |
| --- | --- |
| CURRENT / REVIEWED_UNCHANGED | 새 자료까지 읽었고 현재 내용이 유효함 / 확인 후 결론 유지. |

최신 지표와 이전 보고서를 함께 보여줄 수는 있다. 단 보고서가 사용한 숫자·사건 버전을 보존하고 REVIEW_PENDING을 전면 표시한다. 호환되지 않는 낡은 매수 의견은 현재 판단으로 게시하지 않는다.

오늘 파일을 저장했다는 뜻과 오늘 자료를 검토했다는 뜻은 다르다. 마지막 수집 확인 시각, 실제 자료 기준일, 보고서 작성일, 최종 분석 검토 시각을 각각 보존한다.

# 20. 중간에 꺼져도 전체를 다시 만들지 않는다

국내주식 앱 V3 | 제작 기준

## 종목별 작업 장부

정본 대상 목록에서 작업을 만들고 회사·사건·정책 버전으로 중복 키를 만든다. QUEUED → RUNNING(기한 있는 임대) → DONE / RETRY / QUARANTINED 상태를 저장한다. 실행 번호를 완료 개수처럼 세지 않는다.

## 이전 작업자가 뒤늦게 돌아와도 덮어쓰지 못하게

작업 임대 토큰을 바꾸고 오래된 작업자의 저장을 거부한다. 신규 버전보다 작은 순서 번호의 결과도 거부한다. 새 결과와 알림 발행 목록을 하나의 DB 트랜잭션으로 저장한다. 실패하면 둘 다 되돌아간다. [S18]

## 한 기업 실패는 그 기업에만

500개 중 1개가 다른 회사 자료를 섞으면 그 1개 결과만 격리한다. 나머지 499개는 검증한 범위로 저장·게시한다. 이전 정상본이 있으면 원래 날짜와 경고를 붙여 제공한다.

## 복구 파일에 넣을 것

정본 목록 해시, 코드/정책/자료 버전, 완료된 종목과 파일 해시, 미완료 사유, 임대 상태, 다음 작업, 실제 빌드 산출물, 검사 기록을 담는다. 비밀키·실계좌 토큰·사용자 민감정보는 넣지 않는다.

이번 참고 엔진에서 실제로 확인: 137번째 강제 중단 뒤 136개 보존, 재시작 후 364개만 처리하여 500개. 단 이것은 가상 자료를 넣은 로컬 DB 시험이지 실제 기업 보고서 500개 완성이 아니다. [E-S03]

# 22. 비용이 새지 않게 설계한다

국내주식 앱 V3 | 제작 기준

## AI는 새 사건이 있는 종목에만 쓴다

시세 가져오기, 10지표 산술, 중복 제거, 정책 점수, 출처 ID 대조에는 생성형 AI를 매번 호출하지 않는다. 보고서는 최초 전체 생성과 중요한 변경의 재검토에 비용이 집중된다.

모델 비용 = 호출 대상 수 × (입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가) / 1,000,000 × 호출 단계 수. 여기에 서버·DB·저장·뉴스/시세 계약·세금·환전·재시도 비용을 따로 더한다.

| 완전 가정한 계산 예시 | 금액 · 현재 견적 아님 |
| --- | --- |
| 가정 | 3,000종목, 변경 150개/일, 30일, 단계당 입력 8천·출력 2천 토큰, 2단계. |
| 가정 단가 | 입력 100만 토큰당 $1, 출력 $4. 특정 서비스 가격이 아니다. |
| 최초 생성 | 모델 부분만 $96. |
| 변경분만 한 달 처리 | 모델 부분만 $144. |
| 매일 전체를 다시 생성 | 모델 부분만 $2,880. 같은 가정에서 변경분 처리보다 20배. |

## 강제 상한

추가 과금 승인 전 한도 0. 승인 후에도 작업·일·월별 예산을 저장한다. 병렬 작업은 호출 전에 예산을 원자적으로 예약한다. 중복 작업은 두 번 예약하지 않는다. 한도 도달 시 이전 정상본과 지연 상태를 유지한다.

429는 Retry-After를 존중하고 지수 백오프와 무작위 지연을 사용한다. 401/403은 권한 문제를 우회하거나 무한 재시도하지 않는다. 배포·Actions·유료 실행 실패 시 최초 이후 재실시 최대 3회, 승인된 비용 상한 내에서만 수행하고 이후 중단·재승인한다.

로컬 시험에서 16개 동시 작업자가 예산 1,000단위에 각 100단위 요청 100개를 보냈을 때 10개만 승인됐다. 가상 예산이며 실제 결제는 없었다. [E-S06]

새 국내 앱은 기존 미국 앱과 별도 코드·DB·배포 환경으로 만든다. 읽어서 재사용할 수 있는 부품은 확인 후 가져오되 기존 정상 운영값을 삭제·수정하지 않는다.
